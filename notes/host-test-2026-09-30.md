## Bug 1: fullscreen / maximized pause never fires on KDE Plasma (pre-existing)

**Fixed:** option (a). `display_session.zig` decodes `set_window_observation_state` and feeds `setWindowFlags`; reports against another config generation are ignored. **Seen working on the owner's Plasma, evening of 2026-09-30** (`windows: fullscreen=true` / `maximized=true` lines and `none -> pause` for both).

A real fullscreen Konsole (verified by screenshot: no panel visible) produced **no**
`none -> pause` and **no** `display 1: windows: fullscreen=...` log line. The only
`windows:` line ever logged is the one at register (`fullscreen=false maximized=false
focused=true`), so the plugin's updates never reach the rules.

Root cause (bits and QML are fine; it is the protocol handshake):

1. `daemon/display_session.zig:174`: when the client declares window observation,
   zmurald sends `set_window_observation_config` (generation 0) at register.
2. `third_party/waywallen-display/src/display.c` `waywallen_display_set_window_state()`:
   `if (d->has_window_observation_config) return WAYWALLEN_ERR_STATE;` — once a config
   exists the library refuses the plain `set_window_state` path.
3. `third_party/waywallen-display/plugins/qml/WaywallenDisplay.cpp:944`: with a config
   the QML plugin therefore sends `set_window_observation_state` (opcode 15) instead.
4. `daemon/display_session.zig:145`: `.set_window_observation_state` → `return .none`.
   The flags are discarded. `Session.conditions` is frozen at connect time forever.

Fix options: (a) decode `set_window_observation_state` (generation + flags) and feed
`setWindowFlags`, or (b) don't send the observation config at all so the plugin keeps
using `set_window_state`. (a) keeps the exclusion machinery for later. Add a
`display_session` test for opcode 15 either way.

Headless reproduction, once Plasma is installed here (`tools/kde-test/run.sh` env):
open any window, then force it fullscreen through KWin scripting instead of relying
on `--fullscreen` flags:

    cat > /tmp/fs.js <<'JS'
    for (const w of workspace.windowList())
      if (w.resourceClass.indexOf("konsole") >= 0) w.fullScreen = true;
    JS
    id=$(busctl --user call org.kde.KWin /Scripting org.kde.kwin.Scripting loadScript s /tmp/fs.js | awk '{print $2}')
    busctl --user call org.kde.KWin /Scripting/Script$id org.kde.kwin.Script run

Expect `windows: fullscreen=true` and `none -> pause` in zmurald's log within ~1 s.

## Bug 2: `zmural-settings` crashes on close (SIGSEGV → abort, core dumped)

**Fixed:** the thumbnails are dropped before the backend unloads Cairo. Reproduced headless on Sway with two pictures in the library (exit status 134 before, 0 after). **Seen working on the owner's Plasma, evening of 2026-09-30:** three open/close rounds, `window: closed` each time, zmural kept its pid.

Backtrace from the host core (gdb): `app.deinit` → `dropThumbs` (app.zig:375) →
`gui_cairo.Backend.destroyImage` (gui_cairo.zig:385) → jump to an address with **no
mapping** (libcairo was already unmapped when the core was taken).

Cause: order of defers in `settings/platform_linux.zig::main`. `defer app_mod.deinit()`
is at line 200, `defer app.ui.deinit()` at line 239. Defers run LIFO, so the backend
(which dlcloses cairo) is torn down first, then `dropThumbs` calls the stale
`libs.cairo.surface_destroy` pointer. Fix: call `app_mod.dropThumbs()` (or all of
`app_mod.deinit()`) before the backend's deinit — e.g. move the deinit defer below the
backend's, or make `Backend.deinit` the last thing. Reproduce headless: open the settings
window on Sway and close it with `zmural-test-input`; check `$?` and the journal.

## Bug 3: zmurald leaves `zmural-settings` as a zombie

**Fixed:** zmurald keeps the pids of the windows it starts and collects them on its poll tick (`Children` in `runtime_linux.zig`); a window killed by a signal is logged. **Moot since the settings window became a thread inside zmural (same day); no defunct process seen in the evening pass.**

`daemon/runtime_linux.zig:258` spawns the window with `std.process.spawn` and never
waits on it. After the crash above (and after any normal close) `ps` shows
`[zmural-settings] <defunct>` with zmurald as parent until zmurald exits. Keep the
child handle and reap it (a `SIGCHLD` source next to the renderer reapers, or waitpid
with `WNOHANG` on the poll tick).

## Still open from 2026-09-28

- Hardware decode: mpv `hwdec=auto-safe` tries Vulkan h264 first, RADV refuses
  ("Device does not support decoding h264", 3 errors per start), VAAPI unused.
  **Explained and half fixed 2026-09-30** (MILESTONES M6, "Hardware video decoding"):
  zmural never told mpv which GPU to use, so VA-API could not be used for any codec
  (fixed); and Fedora's Mesa *and* FFmpeg leave H.264 out, so an H.264 wallpaper is
  decoded on the CPU until the host has RPM Fusion's `mesa-va-drivers-freeworld` and
  `libavcodec-freeworld` (a host-side install, the owner's call), or the wallpaper is
  re-encoded to AV1 or VP9.
- Noise per start: `Cannot load libcuda.so.1`, RADV non-conformant warning.

12. **The settings window is frozen for about 4 s after it opens** (the owner: "lags for a
    few seconds before becoming responsive"; KWin captions it "(Not Responding)" meanwhile,
    which is finding 5). Measured from the host with `/proc/<tid>/wchan`+`syscall` sampling
    and `busctl monitor`: the window thread sits in `read()` on its **D-Bus** fd (not the
    control socket, not Wayland) for 2.0 s, twice. Cause, in `src/os/dbus.zig` `call()` and
    `src/settings/platform_linux.zig`:
    1. The window asks the portal `ReadOne org.freedesktop.appearance color-scheme`.
    2. While waiting for that reply, KDE's portal broadcasts three
       `org.freedesktop.portal.Settings.SettingChanged` signals for
       `org.kde.VirtualKeyboard` (`active`, `activeClientSupportsTextInput`, `visible`): it
       does so every time a window takes focus.
    3. `call()` hands every non-matching message to the hook; the hook treats any
       `SettingChanged` as a theme change and calls `theme()` → `readSetting()` →
       `call(ReadOne)` **re-entrantly** inside the outer `call()`.
    4. The inner `call()` reads the outer call's reply, sees the wrong `reply_serial`, and
       drops it. Three ReadOne calls go out within 1 ms (seen on the bus at 12.513) for
       three signals; the innermost gets its own reply, each outer one never does.
    5. Each orphaned outer `call()` then waits out `SO_RCVTIMEO` = 2 s, fails, and
       `readSetting` falls back to the portal-v1 `Read`, which succeeds. Two nested levels
       → 12.514 → 14.550 → 16.598 on the bus: about 4 s with no frames and no pong.
    Fix options (any one ends the stall; the first two together are the clean fix): react
    to `SettingChanged` only for the `org.freedesktop.appearance` namespace and the two
    keys used; never call the bus from inside the hook (set a `theme_dirty` flag and re-read
    on the next loop turn); and make `call()` re-entry-safe or assert against it. Reproduce
    anywhere with xdg-desktop-portal-kde: open the window and watch the bus. On the headless
    rigs there is no portal, so the tests never saw it.
    **Fixed 2026-10-01** (3341154): both clean fixes, plus `call()` refusing re-entry (`error.Reentered`, logged). A unit test replays the KDE sequence over a socketpair. Not yet seen on the desktop.
