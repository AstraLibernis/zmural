# zmural adversarial audit

Scope: `src/`, `tools/`, `build.zig`, `build.zig.zon`, `assets/zmural.rc`, `.github/workflows/ci.yml`. Date: 2026-09-26. No project file was modified.

Baseline: `zig build`, `zig build test` and `zig build -Dtarget=x86_64-linux` all succeed. `zsnag` reports only informational R007/R010 notes, no warnings.

## The three most serious findings

1. **H1**: with any pause rule set to `stop`, a stopped renderer is restarted within 2 s, stopped again, and so on. After about 26 s it is marked `failed` permanently, and the wallpaper doesn't return when the game closes.
2. **M1**: a renderer that can't be spawned (a missing `zmural-video.exe`, a squatted pipe name, a WTF-8 file name) retries every 2 s forever and never gives up. Each attempt writes two log lines to a log that is only rotated at startup.
3. **M2**: the control pipe `\\.\pipe\zmural-%USERNAME%-control` can be pre-created by any local account. zmurald then reports "already running" and exits, or hands its `--apply` path to the squatter, and the CLI talks to the squatter without checking who it is.

## HIGH

### H1: policy `stop` turns into a restart loop, then a permanent `failed` state
- **Where:** `src/daemon/runtime_windows.zig:703-709` (enact stop), `:781-787` (WM_RENDERER end-of-connection), `:345-358` (crashed), `:556-574` (ready), `:711-715`
- **What's wrong:** `enact(.stop)` sends `stop`, calls `reap(r)` and sets `r.state = .policy_stopped`. `reap` cancels the pipe and waits for the reader thread. The reader thread (`pipe.zig:285`) always posts a final `WM_RENDERER` with LPARAM 0 before it exits, so that message is already queued. When it is handled, the guard at `:783` skips only `quitting`, `waiting_restart` and `failed`, not `policy_stopped`. It logs "connection ended", calls `reap` (a no-op) and then `crashed(r)`, which sets `state = .waiting_restart`. `tick()` then restarts the renderer. On `.ready`, `enact(r, desiredFor(r)=stop, fresh=true)` stops it again, and the cycle repeats with backoff of 2, 4, 8 and 10 s. On the 5th "crash", about 26 s after the first and so within `crash_window_ms`, the renderer is marked `.failed`. Once the situation clears, `evaluate()` → `tick()` → `enact(r, .none)` finds `state == .failed`, which is neither `policy_stopped` nor `running`, and returns (`:711-715`). Nothing ever restarts it until a new wallpaper is applied.
- **Failure scenario:** in `settings.toml`, `[pause] fullscreen = "stop"` (the file documents this as "close the wallpaper completely... it starts again when the situation is over"). Start a fullscreen game:
  - zmurald spawns zmural-video (libmpv plus hwdec init) four more times during the game's first ~30 s, which is exactly when the user wants zero load. Each spawn also attaches desktop windows.
  - After the game exits the desktop stays static until the user applies a wallpaper again.
  - The same happens when a `stop` rule fires while the renderer is still `.starting`: `send` on the unconnected pipe fails → kill → reader ends → same path.
- **Evidence:** traced `enact`→`reap`→`readerMain:285`→`controlProc:781-787`→`crashed`→`tick:636`→`start`→`onRenderer(.ready):574`→`enact`. `crashed` counts the crashes, and `now - started_ms` is under 30 s after the first loop, so the count is never reset.
- **Fix direction:** ignore the end-of-connection message when `state == .policy_stopped`, or mark the reap as intentional. Also don't let `tick()` restart a renderer whose `applied == .stop`.

## MEDIUM

### M1: start failures never give up (stale or zero `started_ms`)
- **Where:** `src/daemon/runtime_windows.zig:295-324`, `:345-347`
- **What's wrong:** `started_ms` is set only after a fully successful `start()` (`:316`). `failedToStart` → `crashed` computes `now - r.started_ms > stable_after_ms`. For a renderer that never started, `started_ms == 0`, so on any machine up for more than 30 s the crash counter is reset to 0 every time. `crashes` stays at 1, the delay stays at 2 s, and `give_up_after` is never reached. The same holds when a previously good renderer starts failing more than 30 s after its last successful start.
- **Failure scenario:** the user copies only `zmurald.exe` and `zmural-watchdog.exe` and applies a video, or `CreateProcessW` fails (AV block, Smart App Control), or the pipe name `\\.\pipe\zmural-<pid>-r<id>-<n>` is squatted (predictable once the daemon PID is known), or the path is WTF-8 (L4). The result is an endless 2 s spawn-retry loop and about 86k log lines a day (L5).
- **Evidence:** traced `start()` → `failedToStart` → `crashed`, with `started_ms` only written at `:316`.

### M2: control pipe can be squatted, and the server is never authenticated
- **Where:** `src/daemon/main.zig:128` (name from `%USERNAME%`), `:147-160`; `src/protocol/pipe.zig:172-173` (`ERROR_ACCESS_DENIED` → `InUse`); `src/sdk/control_client.zig:251-264`; `src/cli/main.zig:101`
- **What's wrong:**
  - Pipe names live in one machine-wide namespace. Any local account (or another session) can create `\\.\pipe\zmural-alice-control` first with a permissive DACL. The daemon's `FILE_FLAG_FIRST_PIPE_INSTANCE` create then fails with ACCESS_DENIED, which the code reads as "another zmurald is running" (`error.AlreadyRunning`).
  - Without `--apply` the daemon logs "already running" and exits: a denial of service at every login.
  - With `--apply`, and for every `zmural` CLI call, the client connects to the squatter and sends it the wallpaper path, then trusts its replies.
  - Also, `%USERNAME%` isn't unique (a local and a domain account with the same name, and the variable is user-controlled), and the client never checks the server's owner or process (`GetNamedPipeServerProcessId`, then compare the token SID).
- **Evidence:** code path traced. SQOS identification-only limits impersonation, so the impact is DoS and information disclosure, not privilege escalation. Not exploited live.
- **Fix direction:** name the pipe by user SID plus session id (or put it under `\Sessions\<n>\BaseNamedObjects`/`LOCAL\`-style namespacing). Verify the server's owner SID after connecting. Don't treat ACCESS_DENIED as proof that zmurald is running.

### M3: renderer `WM_PLAYER_GONE` destroys other in-flight teardowns
- **Where:** `src/sdk/windows_renderer.zig:409-416` (and `removeSurface:192-207`, `WM_DESTROY:444-458`)
- **What's wrong:** surface ids are monitor indices and are reused at once: `add_surface` right after `remove_surface`, or right after Explorer destroyed the window. Several slots with the same id can be `closing` at once, each with its own `mpv_terminate_destroy` thread. The first `WM_PLAYER_GONE(id)` loop clears **every** closing slot with that id and `DestroyWindow`s their HWNDs, including slots whose mpv is still tearing down inside that window. The module header says exactly this can deadlock (mpv's threads SendMessage to our window while we tear down its parent).
- **Failure scenario:** Explorer restarts. Explorer destroys the surface windows (`WM_DESTROY`, teardown A starts). The daemon re-attaches with remove and add (surface B, new player). A second reattach 500 ms later (TaskbarCreated plus WM_DISPLAYCHANGE, or the stale-host retry in L1) removes B (teardown B starts) and adds C. When A finishes, `WM_PLAYER_GONE(i)` destroys B's window while teardown B is still running.
- **Evidence:** traced. The timing overlap was not reproduced (running renderers was out of scope). A fix: carry a per-teardown token, such as the slot index or HWND, in the message instead of the surface id.

### M4: duplicate library entries make Next stick forever
- **Where:** `src/daemon/library.zig:36-41` (no de-dup), `:65-73` (`step` finds the first match)
- **What's wrong:** `scan` concatenates every folder's results with no de-duplication, and `settings.library_dirs` is appended to the two defaults (`main.zig:141-145`). A folder listed twice, or a folder plus one of its subfolders (subfolders are scanned one level deep), yields duplicate paths that sit next to each other after sorting. `step(current, forward)` finds the first copy and returns the next item, which is the same path. Each "Next" then goes through `setWallpaper` → `reroute`, which kills and respawns the renderer for the same file.
- **Evidence (reproduced):** a copy of `library.zig` in %TEMP%, with folders `[wp, wp\sub]` holding `a.mp4` and `b.mp4`:
  ```
  count=4 (a, a, b, b)
  next(a.mp4) -> a.mp4   (x4)
  ```
- **Fix:** de-duplicate (case-insensitive) after sorting, or step past entries equal to the current one.

### M5: untrusted media is decoded with the full user token and no sandbox
- **Where:** `src/os/process.zig:141-156` (plain `CreateProcessW`; the job only sets `KILL_ON_JOB_CLOSE`), `src/sdk/windows_renderer.zig:230-250` (mpv options)
- **What's wrong:**
  - Wallpapers are the main untrusted input (downloaded packs, Lively imports on the roadmap). They are demuxed and decoded by FFmpeg inside libmpv in a process with the user's full medium-IL token, no low-IL or AppContainer, no job UI restrictions, and the daemon's environment and CWD.
  - mpv defaults stay on: `ytdl` (the built-in `ytdl_hook` runs `yt-dlp` from PATH/CWD for URLs), and playlist or EDL content detection by file content. A file named `x.mp4` holding an m3u or `# mpv EDL v0` header can make mpv open other local files or remote URLs.
  - `settings.toml`'s `wallpaper` is not validated at all, unlike `apply`'s `playable()`.
  - A future `set_property` passes manifest-controlled names straight into mpv properties (`windows_renderer.zig:144,286-296`), which is a dangerous surface once manifests are wired up.
- **Evidence:** the absence of restrictions is confirmed from the code. The exploit chain is SUSPECTED, not tested.
- **Fix direction:** set `ytdl=no`, `load-scripts=no`, `input-ipc-server=` (empty), and an allowlist for manifest properties. Consider a restricted or low-IL token for renderers, plus job limits (`JOB_OBJECT_UILIMIT_*`, `ActiveProcessLimit`).

## LOW

### L1: `reattach()` continues with a stale `Host`
- **Where:** `runtime_windows.zig:234-244`, `:612-631`
- `attachHost()` returns early on `Host.init` failure without clearing `rt.host`. `reattach()` checks `if (rt.host == null) return;`, which is always non-null after the first success. It then runs `refreshScreens`/`reroute` or remove+add surfaces against the dead Progman/WorkerW. The resulting `.window` attaches fail and log errors, and renderers recreate windows twice per Explorer restart, which makes M3 more likely. Traced: `rt.host` is only ever assigned at `:240`.

### L2: control server use-after-free on OOM
- **Where:** `control_windows.zig:41-55`
- `startReader` launches a thread that holds `&c.conn` before `s.clients.append` can fail. On `error.OutOfMemory` the errdefers close the pipe handles and `destroy(c)` while the thread is blocked in `ConnectNamedPipe`/`WaitForMultipleObjects` on them. Fix: `ensureUnusedCapacity` before starting the thread.

### L3: `--monitor` is accepted everywhere and ignored
- **Where:** `cli/main.zig:15-18,55-61`; `protocol/control.zig:139-142`; `runtime_windows.zig:412-447`
- `zmural apply X --monitor m-…` and `pause/play/next --monitor` succeed and reply `ok`, but `handleRequest` never reads `a.monitor` or the `Target`. The action applies to every monitor, and the user is told it worked.

### L4: WTF-8 file names vs strict UTF-8 conversions
- **Where:** `runtime_windows.zig:547` (`playable`), `os/process.zig:136-138` (`spawn`), `sdk/control_client.zig:233`
- On Windows, `std.Io.Dir` iteration yields WTF-8 (`lib/std/Io/Dir.zig:51`). The code uses `std.unicode.utf8ToUtf16LeAllocZ`, which rejects encoded surrogates.
  - Experiment: `utf8ToUtf16LeAllocZ("a\xED\xA0\x80b.mp4")` → `error.InvalidUtf8`; `wtf8ToWtf16LeAllocZ` accepts it.
  - Such a file in the library can be selected by Next (no `playable` check on that path), `spawn` fails, and M1's endless retry follows. Use the `wtf8*` converters for paths.

### L5: unbounded log growth at runtime
- **Where:** `os/logfile.zig:95-117`; `sdk/windows_renderer.zig:320-324`; `runtime_windows.zig:583`
- Rotation happens only in `open()` at startup. Every mpv `warn` or `error` line is forwarded over the pipe and logged. A file that triggers a warning per frame (a broken timestamp, say) at 60 fps, or M1's loop, grows `zmurald.log` without limit for as long as the daemon runs, which can be weeks with autostart.

### L6: control-pipe starvation and blocking writes on the UI thread
- **Where:** `control_windows.zig:58-91`; `pipe.zig:75-86`
- Only one listening instance exists until a client says `hello` (`:84`). A client that connects and sends nothing holds it, and every other `zmural` call fails after `WaitNamedPipeW(2000)` → `Timeout` (confirmed by trace).
- Separately, `reply()`/`send()` run `writeAll` on the UI thread with `GetOverlappedResult(bWait=TRUE)` and no timeout. A same-user client that keeps sending `status` without reading fills the 64 KiB buffer and freezes the whole daemon: tray, pausing, renderers (SUSPECTED, not reproduced).
- Both need a same-user process, so they are robustness issues rather than a privilege boundary.

### L7: the renderer's `.window` HWND and the pipe client are not checked
- **Where:** `runtime_windows.zig:576-582`, `pipe.zig:117-140`
- The daemon reparents whatever HWND the renderer reports (any window of any same-IL process) into Progman or WorkerW. It also never checks that the client that connected to `\\.\pipe\zmural-<pid>-r<id>-<n>` is the child it spawned (`GetNamedPipeClientProcessId == child.pid`). A compromised renderer (see M5), or a same-user process that wins the connect race, can pull arbitrary windows behind the desktop. There is no privilege gain, but it is cheap hardening.

### L8: lost `CancelIoEx` can hang shutdown
- **Where:** `control_windows.zig:109-126`; `pipe.zig:64-66, 268-285`
- `reap()` relies on `CancelIoEx` to wake the reader, then waits `INFINITE`. If the reader is between iterations (after `PostMessageW`, before the next `ReadFile`), nothing is cancelled and the next `ReadFile` blocks until the client disconnects.
- Renderer reaps are safe because `kill()` breaks the pipe first. Control clients have no such fallback, so shutdown can hang while a long-lived client (a future UI) stays connected.
- SUSPECTED: the window is small. Fix: a stop event checked in the loop, or `DisconnectNamedPipe` before waiting.

### L9: no logoff or shutdown handling
- **Where:** `runtime_windows.zig:761-840`
- GUI processes get `WM_QUERYENDSESSION`/`WM_ENDSESSION`, not console control events. Neither is handled, so at logoff the process is terminated without `shutdown()`: no `refreshStaticWallpaper`, no clean watchdog kill. The watchdog then runs `SPI_SETDESKWALLPAPER` in the middle of logoff. Settings are unaffected (saved on every change).

### L10: tray left click may fire twice
- **Where:** `tray_windows.zig:96-100`
- With `NOTIFYICON_VERSION_4`, a left click produces `WM_LBUTTONUP` and then `NIN_SELECT`, and both are accepted. The second arrives while the first `TrackPopupMenuEx` is modal and re-enters `onTray`. The result is a failed nested menu, or the menu reopening right after it closes. SUSPECTED (depends on shell behaviour, not tested).

### L11: `refreshStaticWallpaper` can change the user's wallpaper mode
- **Where:** `os/desktop.zig:14-19`
- It reads `SPI_GETDESKWALLPAPER` into a MAX_PATH (260) buffer and writes the same path back with `SPI_SETDESKWALLPAPER`. For slideshow or Spotlight users, the GET returns the current transcoded image, and SET pins it, which likely ends slideshow mode. Paths longer than 259 characters get truncated or fail. SUSPECTED; it only runs in the classic layout.

### L12: `--demo` is unusable as built
- **Where:** `build.zig:52-54` (zmurald is `subsystem = .windows`), `daemon/demo.zig:53,67,73…`
- All demo output goes through `std.debug.print` to a stderr that a GUI-subsystem process doesn't have. The "press Ctrl+C to stop" hint can't work because there is no attached console, so the demo can only be stopped with `taskkill`.

### L13: `playable()` is too permissive and can block
- **Where:** `runtime_windows.zig:545-550`
- `GetFileAttributesW != INVALID` accepts directories. `zmural apply C:\Windows` routes a directory to zmural-image, and mpv fails with a restart or failed-state loop. A UNC path to an unreachable host blocks the UI thread for the SMB timeout, around 20-60 s.

## NIT

### N1: dead or unwired code
- `src/daemon/playlist.zig`: `Playlist` is used only by its own tests. Nothing in the daemon references it; the tray's Next/Previous uses `Library.step`.
- `src/core/manifest.zig`: exported from `zmural.zig:16` and never used.
- `src/core/monitor.zig`: `parseEdid`/`fromEdid` are unused. The daemon only uses `fromConnector(name, w, h)`, so a resolution change changes the "never changes" monitor ID (`:5`), and a game switching resolution triggers a full `reroute`.
- `src/core/layout.zig`: `place()` is unused (the renderer uses mpv `panscan`/`keepaspect`).
- `src/hosts/windows/workerw.zig:157-161` `Host.detach` is unused; `restoreStaticWallpaper` is used only by the demo.
- `src/core/policy.zig`: `Rule.resume_delay_ms` is never read (the daemon uses `settings.resume_after_ms`), and `Condition.isPerMonitor` is unused. `session_inactive`, `game_mode` and `other_audio` are never produced on Windows but are still accepted in `[pause]`.
- `src/daemon/settings.zig:28,38-40`: `arrangement`, `blur_when_paused`, `transition`, `transition_ms` are neither parsed nor written; `fps_cap` isn't in the file either.
- Protocol:
  - `ToRenderer.set_property/seek/screenshot` are handled by the renderer but never sent.
  - `FromRenderer.loaded/frame_ready` are ignored.
  - `control.Event.wallpaper_changed/playback_changed` are never pushed.
  - `transport.Endpoint.display` and `hosts.linux.backend.pick` are unused.
  - `daemon.zig` `Daemon` (Linux) prints and exits.
- `src/os/win32.zig`: `ERROR_BROKEN_PIPE`, `STARTF_USESTDHANDLES`, `HANDLE_FLAG_INHERIT`, `SetHandleInformation`, `GetExitCodeProcess`, `STD_INPUT_HANDLE`, `WS_VISIBLE` are unused.
- `.html`/`.htm` go to `zmural-web.exe`, which is `sdk.renderer.stub` and exits 1. `apply index.html` is accepted and then crash-loops into `failed` after 5 spawns.

### N2: small leaks and races
- `sdk/windows_renderer.zig:95`: the reader thread handle is discarded (`_ = try ...startReader`), which leaks a handle.
- `os/libmpv.zig:240-249`: `Api.load` leaks the loaded module on `SymbolMissing`/`UnsupportedVersion`.
- `watchdog/main.zig:75`: it watches a PID rather than an inherited process handle, so there is a PID-reuse window if the daemon dies before `OpenProcess`.
- `sdk/control_client.zig:236`: paths of 1024 UTF-16 units or more are silently sent unresolved (relative), and the daemon then resolves them against its own CWD.
- `daemon/main.zig:123`: a long `%LOCALAPPDATA%` makes `bufPrint` fail, and the log silently lands in `%LOCALAPPDATA%` itself.
- `daemon/runtime_windows.zig:363-371`: `retire()` sends `stop` and then `reap()` kills immediately (`hasExited` is almost always false), so the "polite" stop has no grace period.
- `tools/icongen.zig:374-381`: buffers are leaked if an allocation fails mid-loop (the `defer` is registered after the loop). This only matters for the build tool.

## Test gaps
- **`runtime_windows.zig` state machine**: `enact`/`evaluate`/`tick`/`crashed` and the WM_RENDERER end-of-connection path. H1 and M1 would both be caught by a unit test if this logic were separated from Win32. There is no test of relax delays, stop and restart, the give-up window, or a shared renderer's weakest-action rule.
- **`control_windows.zig`**: hello gating, re-listening after a greeted or ungreeted client, version mismatch, drop — none tested.
- **`pipe.zig`**: framing over a real pipe, `waitForClient` timeout and abort, cancel, partial reads — none tested (a loopback pipe test is feasible in-process).
- **`settings.Store`**: `load` (BOM, read-only on parse error, not overwriting) and `save` (atomic rename) — untested.
- **`library.Library.scan`**: depth, filtering, sorting, duplicates (M4) — untested; only `step` on hand-built lists is tested.
- **`facts.collect`/`frameBounds`/`exeName`**: OS-bound and untested. `hidesDesktop` and `deriveMonitor` are tested.
- **`windows_renderer.zig` surface lifecycle**: add/remove/destroy/player-gone — untested.
- **`process.spawn`**: end-to-end argv round trip — untested; only the quoting is tested.
- **`logfile`, `autostart`, `desktop`**: untested.

## Checked and refuted
- `HKEY_CURRENT_USER` as a zero-extended `@ptrFromInt(0x80000001)` (C sign-extends): a read-only `RegOpenKeyExW` experiment returned 0, so it works.
- `std.Io.Dir.rename` over an existing file (used by `Store.save`): the experiment shows it replaces the file.
- Parser robustness: fuzzed `toml.parse` and `wire.decodeFrame`/`decodeMessage` for control and renderer messages with 300k random or structured inputs. No panics, and a 50k-case `writeString`→`parse` round trip matched every time.
- Win32 layouts and signatures: `OVERLAPPED`, `STARTUPINFOW`, `JOBOBJECT_*`, `NOTIFYICONDATAW` (976 bytes, asserted), `MONITORINFOEXW`, `PAINTSTRUCT`, `SYSTEM_POWER_STATUS`, `WNDCLASSEXW`, and the handle-return conventions (`CreateNamedPipeW`/`CreateFileW` vs `INVALID_HANDLE_VALUE`, others vs NULL) are correct.
